# Дизайн: рідший global backoff, довші/частіші активні проходи

**Дата:** 2026-08-17
**Трек:** crawler resilience (окрема сесія; гілка від `main` → merge назад)
**Статус:** дизайн затверджено, чекає на імплемент-план

## Проблема (діагноз)

Global backoff краулера частішає й зливається в довгі смуги простою. Причина — **не поганий IP**, а два дефекти машинерії:

1. **Мертві бекенди отруюють пул.** У `ddgs`-пулі 5 бекендів `google,startpage,duckduckgo,yahoo,brave`. Бекенди `google` і `startpage` структурно важкі (важкий анти-бот) і падають незалежно від якості IP. Лічильник `fails` у `SearchState` скидається **лише на success** (`search_state.py:83`), тож `google` накопичив 40 провалів поспіль і вічно тягне пул до стану «жоден не здоровий».

   Доказ, що це не бан IP: у зрізі стану `yahoo=1`, `brave=1`, `duckduckgo=3` — здорові з того самого IP; мертві лише `google=40`, `startpage=8`.

2. **Фіксований 6-год «все-або-нічого» бекоф.** Коли `_take_next_healthy()` не знаходить жодного здорового бекенда, `set_global_backoff(6 год)` (`providers.py:89`, `config.py:30`). Епізод — завжди фіксовані 6 год, і переармовується одразу, тільки-но спав, поки бекенди лишаються мертвими → активні вікна коротшають, простій зливається в довгі смуги.

3. **Під бекофом глушиться ВЕСЬ пошук.** `run_active(ddg_allowed=False)` під бекофом викликає лише `SearchPass.drain()` (`runner.py:131`) — жодного нового пошуку від будь-якого провайдера. Немає незалежного каналу discovery, який пережив би DDG-бекоф.

## Мета

- Global backoff — **рідший** (усунути тригер).
- Активні проходи — **довші й частіші** (не зупиняти discovery на 6 год; тримати незалежний канал).

## Наскрізний принцип

**Бекоф — властивість одного бекенда/провайдера, а не всієї системи.** Мертвий бекенд не має зупиняти пул; недоступність DDG не має зупиняти discovery, якщо живий інший провайдер.

## Фаза 1 — Гігієна здоров'я бекендів

**Файли:** `crawler/crawler/discovery/search_state.py`, `crawler/crawler/discovery/providers.py`, `config.py`

Ввести **карантин** структурно-мертвих бекендів, щоб вони не рахувалися в рішенні «жоден не здоровий».

### Стан бекенда (`SearchState`)
Запис бекенда розширюється полями карантину. Концептуально:
```
backends[name] = {
  "fails": int,
  "cooldown_until": float,      # транзієнтний експоненційний кулдаун (як зараз)
  "quarantined_until": float,   # НОВЕ: 0.0 = не в карантині
  "next_reprobe_at": float,     # НОВЕ: коли дозволено 1 пробний запит
}
```

### Правила переходів
- **Вхід у карантин:** у `record_block`, якщо `fails >= quarantine_threshold` (деф. **6**) → виставити `quarantined_until = now + quarantine_hours*3600` (деф. **24 год**) і `next_reprobe_at = now + reprobe_hours*3600` (деф. **6 год**).
- **Вибір бекенда (`_take_next_healthy`):** карантинений бекенд **пропускається**, ЯКЩО `now < next_reprobe_at`. Коли `now >= next_reprobe_at` — бекенд дозволено **один** пробний запит (ре-проб).
- **Ре-проб success:** `record_success` знімає карантин повністю (`fails=0`, `cooldown_until=0`, `quarantined_until=0`, `next_reprobe_at=0`).
- **Ре-проб fail:** `record_block` лишає карантин, відсуває `next_reprobe_at += reprobe_hours*3600` (не подовжуючи `quarantined_until` нескінченно — просто продовжити цикл ре-пробів, доки `quarantined_until` не спаде природно, тоді бекенд повертається як звичайний кандидат).

### Рішення all-cool
Предикат «жоден не здоровий» рахує бекенд **недоступним**, якщо він або в кулдауні (`now < cooldown_until`), або в карантині без права ре-пробу (`now < next_reprobe_at`). Карантинений бекенд, готовий до ре-пробу, вважається доступним (щоб ре-проб стався). Мертві google/startpage у карантині → пул для all-cool = живі бекенди → all-cool рідкісний.

### Конфіг (Фаза 1)
```
search_backend_quarantine_threshold: int = 6
search_backend_quarantine_hours: float = 24.0
search_backend_reprobe_hours: float = 6.0
```

## Фаза 2 — Прибрати фіксований 6-год global backoff

**Файли:** `crawler/crawler/discovery/search_state.py`, `crawler/crawler/discovery/providers.py`, `crawler/crawler/scheduler.py`, `config.py`

**Прибрати** фіксовану 6-год зупинку. «Global backoff» стає **похідним** зі станів бекендів, а не окремим збереженим полем `next_allowed_at`.

- `in_global_backoff()` → `True`, коли **жоден** не-карантинений (і не готовий-до-ре-пробу) бекенд не здоровий прямо зараз.
- `seconds_until_allowed()` → `min(cooldown_until)` по не-карантинених бекендах, обмежене знизу підлогою `backoff_floor_seconds` (деф. **300**), зверху — наявним `backoff_max_sleep_seconds` (1800) на рівні сну scheduler.
- `providers.py`: замість `set_global_backoff(fixed)` більше нічого не «встановлює» — бекоф уже виражений кулдаунами бекендів. `set_global_backoff` та поле `next_allowed_at` **прибираються** (back-compat: `SearchState.load` ігнорує legacy-поле, якщо є).

6-годинна мертва зупинка → зазвичай хвилини (до найближчого відновлення бекенда). Підлога + наявний per-backend експоненційний кулдаун захищають від довбання ще-затротленого бекенда.

### Конфіг (Фаза 2)
```

# search_global_backoff_hours — DEPRECATED (парситься для back-compat, не використовується)
```

## Фаза 3 — Тюнінг тиску запитів

**Файли:** `crawler/crawler/discovery/providers.py`, `config.py`

- **Адаптивний `min_delay`:** множник паузи між запитами залежно від частки живих бекендів — менше живих → довша пауза (щоб не додавити виживших). Одна чиста функція `_adaptive_delay(healthy_count, pool_size)`; за повного здоров'я поведінка байт-ідентична поточній.
- **Довший `search_cache_ttl_hours`:** підняти дефолт (напр. 96 → 168 год), щоб due-walking рідше пере-шукав ту саму фразу → менше мережевих запитів → менше тротлінгу. Значення — узгодити в імплемент-плані.

Низький ризик; головно config-рівень + одна невелика функція.

## Фаза 4 — Оживити SearXNG як незалежний канал discovery

**Файли:** `docker-compose.yml` (+ `docker/searxng/` конфіг), `crawler/crawler/discovery/searxng_provider.py` (воскресити), `crawler/crawler/discovery/providers.py` (`build_search_plans`), `crawler/crawler/discovery/search_pass.py`, `crawler/crawler/runner.py`, `crawler/crawler/scheduler.py`, `config.py`

### Інфра
- Сервіс `searxng` (образ `searxng/searxng`), `format: [json]` увімкнено, **широкий набір незалежних рушіїв**, що працюють з нашого IP: `duckduckgo, brave, mojeek, qwant, marginalia, wikidata` (google/bing свідомо ВИМКНЕНІ — саме вони капчили нас раніше; Yandex та будь-які рос-рушії ВИМКНЕНІ за правилом проєкту). Тільки внутрішня Docker-мережа, без публічного порту.
- «Ширша функціональність» реалізується саме тут — набором рушіїв в одному контейнері, а не окремими провайдерами (див. «Дослідження провайдерів»).

### Дослідження провайдерів (висновок 2026-08)
Проведено огляд альтернатив DDG/SearXNG. Висновок: **безкоштовного drop-in кращого за DDG+SearXNG немає.**
- **Brave Search API** — безкоштовний тир убито (початок 2026), тепер метерд-білінг → платний, поза скоупом.
- **Mojeek API** — лише B2B/платний (безкоштовно тільки trial).
- **Whoogle** — лише Google → з нашого єдиного IP та сама CAPTCHA, що вбила SearXNG раніше; гірше.
- **4get / LibreY / LibreX / MetaGer** — та сама метапошукова модель, без переваги.
- **Ключове:** brave/mojeek/qwant/startpage/ddg **уже досяжні** через `ddgs` і через SearXNG без ключів → окрема інтеграція = дублювання + платно. Тому breadth беремо конфігом рушіїв SearXNG, а не новими провайдерами.

### Провайдер
- Воскресити `SearxngProvider` з git `834ce30`, адаптувати під поточні `SearchProviderPlan`, `classify_candidate`, `SourceCandidate`. Запит до локального `http://searxng:8080/search?format=json`.
- **Власне здоров'я:** SearXNG-план має окремий `succeeded`/бекоф, **незалежний** від DDG-станів. Внутрішній per-engine бекоф робить сам SearXNG.

### Рефактор незалежності (ядро фази)
1. **`SearchPass.run()` ітерує ВСІ плани** (зараз хардкод `self._plans[0]`, `search_pass.py:44`). Кожен провайдер сам-гейтиться своїм здоров'ям; `drain()` (кеш) виконується один раз незалежно від провайдерів. Порядок/дедуп кандидатів зберегти.
2. **`run_active` більше не глушить увесь пошук під DDG-бекофом.** DDG-план сам повертає `[]` (`in_global_backoff`), SearXNG-план працює → активний прохід дає нові кандидати навіть під DDG-бекофом. `drain()` лишається як був.
3. **`scheduler.step()` узагальнюється з «DDG» на «будь-який провайдер»:**
   - Живий **хоч один** провайдер → повний активний прохід + сон `active_delay`.
   - **Усі** провайдери сплять → DDG-незалежний прохід (drain+feeds+harvest) + passive-if-due + сон до найближчого відновлення (`min` по провайдерах, з підлогою/капом).
   - Passive-overdue safety net — без змін.
4. **`site:` теж йде через будь-який живий провайдер.** `site:` — це пошуковий оператор у ключовому слові, а `ActiveDiscovery` провайдер-агностичний; SearXNG виконує той самий active discovery, що й DDG. Зараз `site:`-лег випадково прив'язаний до DDG: `provider_for_site_query()` повертає хардкод `plans[0].discovery` (`search_pass.py:80`, `wiring.py:147`). Змінити на «повернути `discovery` поточно-здорового провайдера» (пріоритет — той самий провайдер, що обслуговує основний search-лег цього проходу). Під DDG-бекофом `site:` виконується через SearXNG → активний прохід (feeds + search + site:) **не калічиться**. Пріоритет треку: усе — насамперед заради активного краула.

### Конфіг (Фаза 4)
```
search_providers: "duckduckgo,searxng"     # додати searxng
searxng_url: "http://searxng:8080"
searxng_engines: "google,bing,duckduckgo,brave,mojeek,qwant,marginalia,wikidata"  # без yandex (правило); google/bing ре-валідовано наживо — працюють з резидентного IP
```

## Тестування (TDD, по фазах)

**Фаза 1:** переходи карантин↔ре-проб у `SearchState`; `_take_next_healthy` пропускає карантинених до `next_reprobe_at`, дозволяє один ре-проб після; ре-проб success знімає карантин, fail відсуває; предикат all-cool виключає карантинених.

**Фаза 2:** `seconds_until_allowed = min(cooldown)` по не-карантинених + підлога; `in_global_backoff` похідний; legacy `next_allowed_at` при `load` ігнорується без падіння.

**Фаза 3:** `_adaptive_delay` монотонно зростає зі зменшенням живих; за повного здоров'я = поточний `min_delay` (байт-ідентично).

**Фаза 4:** парсинг SearXNG JSON (мок-відповідь) → `SourceCandidate` через `classify_candidate`; `SearchPass.run()` ітерує кілька планів і зливає результати; **незалежність** — DDG у бекофі, SearXNG повертає кандидатів, активний прохід непорожній; `provider_for_site_query()` повертає здорового провайдера (DDG у бекофі → віддає SearXNG-discovery, `site:`-лег працює); гілка scheduler «будь-який живий провайдер».

**Регрес:** за одного провайдера / повного здоров'я — поведінка байт-ідентична поточній (одно-провайдерний шлях `SearchPass`, `_adaptive_delay` за повного пулу, scheduler з одним DDG).

## Ризики (ранговано)

1. **Рефактор `SearchPass` `plans[0]`→всі плани** — найгарячіший шлях discovery. Мітигація: одно-провайдерний шлях лишити байт-ідентичним; TDD; регрес-тести наявних сценаріїв.
2. **SearXNG сам тротлиться** зі спільного IP. Мітигація: вибір рушіїв (без google/bing) + внутрішній per-engine бекоф SearXNG; якщо помер — сам-глушиться, падаємо на DDG (не гірше, ніж сьогодні).
3. **Замала підлога бекофу** → довбання ще-затротленого бекенда. Мітигація: `backoff_floor_seconds` (300) + наявний експоненційний per-backend кулдаун.
4. **+контейнер SearXNG** — новий рухомий шматок і споживання ресурсів. Прийнято в рамках «легкої інфри».

## Свідомо поза скоупом (YAGNI)

- **Проксі-пул (Шар 5).** Докази кажуть, що наш IP наразі придатний; безкоштовні/датацентрові проксі радше нашкодять (спалені/капчаться, MITM-ризик), резидентні — платні. Плумбінг `config.proxies` уже є — підключити до пошуку можна пізніше маленькою зміною, якщо впремося в стелю єдиного IP. Відкладання нічого не коштує.
- **Платні пошукові API** (SerpAPI/Brave API/Mojeek B2B) — не в цьому треку.
- **Throttle-immune канали іншої форми (окремий майбутній трек).** YaCy (self-hosted P2P власний індекс) і Common Crawl (bulk-енумерація URL через CDX, лягає в наявну feed-архітектуру) імунні до тротлінгу, але важкі й з непевним/тонким UA-покриттям, поки не наповнимо/не звузимо. Свідомо відкладено, щоб не роздувати поточний трек і не додавати канал без ре-валідації покриття.
- **Російські пошукові сервіси (Yandex XML/Search API тощо)** — виключені назавжди за правилом проєкту (мова/сервіс агресора), у т.ч. як engine у SearXNG.
