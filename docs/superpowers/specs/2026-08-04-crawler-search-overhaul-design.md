# Track B — Active-search coverage overhaul + domain revisit cooldown

**Дата:** 2026-08-04
**Гілка:** `feat/crawler-search-overhaul` (від `main`, ПІСЛЯ Треку A)
**Тип:** crawler-only. Backend/admin не змінюються.
**Передумова:** Трек A (відсів новинних) уже влитий — інакше розширений пошук помножить новинний леак.

## Проблеми (підтверджено фактами з коду/лайву)
- `DomainFeed`/`site:` беруть `registry.top(N)` **щопрохід** (не ротація) → топ-домени ре-краулються кожні ~2 год, поки не опублікуються.
- Грід = **351** (INTENT 13 × AUDIENCE 27); `queries_per_pass=40` → повний обхід ~9 проходів ≈ 18 год, але `TTL=96 год` → проходи 10-48 переганяють кеш (холості повтори).
- `results_per_keyword=7` без пагінації → **новизна лише з НОВИХ фраз**.
- `min_delay=4с` живий → перевантажує бекенди (`google` fails=16, `startpage` fails=8).
- DDG і searxng мають окремі курсори, але **обидва незалежно обходять увесь грід** → дублюють роботу.

## Рішення (оптимальні числа — на фактах)

### 1. Блок-партиція DDG↔searxng зі свапом
- Єдиний `block_cursor` + лічильник `cycle`. `block_size` = **15**/провайдер.
- Щопрохід — два сусідні непересічні блоки `[C]` і `[C+1]`; `block_cursor += 2×block_size` (по завершенні обходу `cycle += 1`).
- **Провайдер за парністю `(block_index + cycle)`:** парний → DDG, непарний → searxng. Тобто кожен блок **щоцикл міняє рушій** (стійкість: що один не знайшов — інший підбере наступний цикл), незалежно від розміру гріда.
- Виконання: **послідовно в межах проходу** (між проходами sleep 2 год домінує; справжні OS-потоки дають ~0 виграшу каденції + ризик до `SearchState`). Якщо колись знадобиться — потоки з інваріантом «стан пише лише головний потік після join».

### 2. Due-query walking
- `SearchPass` бере лише фрази з **простроченим/відсутнім** кешем (пропускає свіжі), просуваючись далі → **щопрохід свіжі мережеві запити**, увесь простір обходиться перш ніж повторити. TTL стає per-phrase кулдауном.

### 3. Розширення простору фраз (max охоплення)
- Додати **місто як справжній множник** по **курованому топ-міст** (~40-50 найбільших/обласних центрів, НЕ всі 1229 — інакше тонни порожніх запитів) → цільовий простір ~**1500-1700** унікальних фраз.
- `results_per_keyword` лишити 7 (новизна — з нових фраз, не пагінації).

### 4. Оптимальні ручки (throttle vs охоплення)
| Ручка | Значення | Факт-обґрунтування |
|---|---|---|
| `block_size` | **15**/провайдер | DDG 15×~20с=~5хв/прохід; по 5 бекендах = 3/бекенд/прохід → ~100с/бекенд — безпечно |
| `SEARCH_MIN_DELAY` | **4с → 20с** | прибирає причину блоків (per-backend ~100с) |
| простір фраз | ~1700 | 351 + куровані топ-міста |
| надійна пропускна | ~180 фраз/добу (DDG сам) | 15 × 12 проходів (2-год цикл) |
| повний обхід | ~7-9 днів (DDG сам), ~5 (з searxng) | |
| `SEARCH_CACHE_TTL_HOURS` | **168** (7 днів) | freshness-floor; due-walking вирівнює обхід↔TTL |

### 5. Domain revisit cooldown (окремий важіль, 21 день)
- `DomainRegistry.seen_within(host, seconds)`; `top(n, known_hosts, cooldown_seconds=0)` виключає хости з `now−last_seen < cooldown`.
- `ActiveHarvester` gate + `DomainFeed`/`site:` беруть top-**доступних** → активний **йде далі по списку**, а не довбає топ; будь-який вже-відвіданий хост — не частіше ніж раз на 21 день. `config.active_revisit_cooldown_days=21`. Class-default 0 = byte-eq.
