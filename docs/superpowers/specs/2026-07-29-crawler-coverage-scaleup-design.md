## 1. Контекст і діагноз

Discovery-архітектура комплексна й працює, але **задроселена**. Крім того, спосіб подачі запитів має структурну ваду для другого пошукового провайдера:

- `wiring.py:116` бере **одну** пачку `search_queries_per_pass` (=40) з `QueryGrid` від `grid_cursor`, зсуває курсор **безумовно** (ще до пошуку), мерджить зі статичними `SEARCH_KEYWORDS`.
- `build_search_provider` повертає **один** `combined(keyword)` — на кожен ключ фанить **усі** ввімкнені провайдери. Тобто додати `searxng` наївно = DDG і SearXNG б'ють **ті самі** запити (0 нового покриття + подвоєний ban-ризик).
- Грід на 78% складається з бренд-фраз, які **дублюються** бренд-домен-фідом (`brand_feed.BRAND_SEEDS` ≡ `query_grid.BRANDS`, резолвиться в домени й фетчиться щопрохід незалежно від пошуку).
- `SEARCH_CACHE_TTL` = 168 год: менший грід → швидший оберт → ре-візит у межах TTL повертає кеш → нема нових сторінок.

## 2. Скоуп

**В скоупі (цей трек, один merge):**
1. **SearXNG/DDG split** (ядро) — окремі query-слайси на провайдера, окремі курсори, advance-on-success.
2. **Бренди з осі гріду** — `build_grid()` генерує лише `intent×audience`. `BRANDS` кортеж лишається (його імпортує `brand_feed`).
3. **Ручки пропускної** (значення): `ACTIVE_FETCH_BUDGET` 20→80, `OSM_FEED_MAX_DOMAINS` 500→1500, `OSM_MIN_POIS` 2→1, `CRAWL_INTERVAL_SECONDS` 21600→10800.
4. **`SEARCH_CACHE_TTL`** 168→96 год (вирівняти під нову каденцію).

**Поза скоупом (окремі задачі беклогу):** city-вісь (#8), page-level dedup (#6), reject-downrank (#9), UX черги (#10), конкурентність (#11). **Auto-publish — ВІДХИЛЕНО.**

## 3. Ядро: SearXNG/DDG split (варіант A — незалежні курсори)

### 3.1 Модель
Одна `QueryGrid`. Кожен пошуковий провайдер має **власний курсор** у `SearchState`:
- DDG → наявний `grid_cursor` (без змін семантики ключа).
- SearXNG → новий `searxng_cursor`, ініціалізований з **офсетом** `len(grid)//2`, щоб за прохід слайси майже не перетиналися (≈2× унікального покриття).

Кожен провайдер за прохід бере свій батч `search_queries_per_pass` від свого курсора. **`combined`-fan-out прибирається.**

### 3.2 advance-on-success (ключова зміна поведінки)
Зараз курсор просувається **безумовно при build**. Стає: курсор конкретного провайдера просувається **лише якщо цей провайдер реально відпрацював** (зробив мережевий пошук без деградації/backoff). Наслідок: throttled-провайдер ретраїть **той самий** слайс наступного проходу замість пробити діру в покритті.

- «Успіх» DDG = після `discovery.run` стан НЕ `degraded_last_call()` і НЕ `in_global_backoff()`.
- «Успіх» SearXNG = провайдер зробив запит без винятку. Потрібен **degraded-сигнал і для SearXNG** (зараз він мовчки повертає `[]` на помилку) — додати легкий прапорець (напр. той самий `SearchState.mark_degraded/clear_degraded`, або власний прапорець провайдера), щоб курсор не рухався на порожньому-через-помилку проході.

**Розташування логіки:** батчинг+advance переносяться з build-time (`wiring.build_runner`) у фазу discovery раннера — бо лише там відомий результат проходу. `build_runner` віддає раннеру **план провайдерів** (список `(provider_name, provider_callable, cursor_key)`), а `Runner` на кожному проході: бере слайс від курсора → `discovery.run(slice)` → якщо не-degraded, зсуває курсор цього провайдера.

### 3.3 Статичні `SEARCH_KEYWORDS`
Куровані пін-запити високоцінні й нечисленні. **Рекомендація:** додаються до слайсу **DDG** (надійніший, курований канал), НЕ дублюються в SearXNG. Зберігає поточну поведінку пінів на основному провайдері.

### 3.4 Зворотна сумісність
- **DDG-only** (`SEARCH_PROVIDERS=duckduckgo`, дефолт): один провайдер, один курсор `grid_cursor`. Поведінка ідентична сьогоднішній **окрім** advance-on-success (курсор не рухається на degraded-проході). Це навмисне покращення; існуючий `test_build_runner_rotates_query_grid_and_unions_pins` (фіксує безумовний advance при build) **оновлюється** під нову семантику.
- **Жоден провайдер** (`search_providers=[]`): discovery None, курсори не рухаються (раніше `grid_cursor` рухався навіть без провайдера — цю ваду прибираємо).

### 3.5 Ban-risk SearXNG
- SearXNG самохоститься (docker), проксює до реальних движків → під навантаженням upstream може забанити інстанс.
- Мітигації: (а) advance-on-success сам по собі гальмує — банутий SearXNG не рухає курсор і не поглиблюється; (б) `search_min_delay` лишається на SearXNG (не прибирати); (в) SearXNG-слайс можна тримати ≤ DDG-слайсу (окремий `search_queries_per_pass` для SearXNG — **опція**, за замовчуванням той самий розмір; вводити лише якщо бан проявиться).

## 4. Бренди з осі гріду

`build_grid()`: ітерувати лише `INTENT_FORMS` (прибрати `*BRANDS` з `for head in (...)`). Грід 1593→351. `BRANDS` кортеж **не чіпати** (інваріант `brand_feed`). Оновити `test`-фікстури розміру гріду. Домен-покриття брендів зберігається через `brand_feed` (перевірено).

## 5. Ручки пропускної (значення)

Задаються у проді в `docker-compose.yml` (crawler `environment:`), окрім інтервалу (root `.env`). **Дефолти в `config.py` рухаємо теж** (щоб намір був справжнім дефолтом, не лише env-override), з оновленням `test_config.py`:
- `active_fetch_budget` 20→80
- `osm_feed_max_domains` 500→1500; `osm_min_pois` 2→1
- `search_cache_ttl_hours` 168→96
- `CRAWL_INTERVAL_SECONDS` 21600→10800 — **лише ops** (`.env`/entrypoint), не в `config.py`.

**OSM force-refresh:** нові OSM-параметри застосуються лише коли кеш `/data/osm_domains.json` протухне (336 год). При деплої — **видалити кеш-файл** один раз, щоб форснути ре-енумерацію. (Ops-крок, без коду.)

## 6. План тестування (TDD)

- **SearchState:** `searxng_cursor` getter/setter/persist; офсет-ініціалізація.
- **Провайдер-план:** `build_search_provider` повертає названі провайдери (не combined); DDG-only = один план-запис; DDG+SearXNG = два записи з різними cursor_key.
- **advance-on-success:** курсор рухається на успішному проході; НЕ рухається на degraded/backoff; кожен провайдер незалежно.
- **Слайси disjoint-ish:** DDG-слайс і SearXNG-слайс за прохід не збігаються (офсет).
- **SearXNG degraded-сигнал:** помилка → порожньо + не-advance.
- **Статичні пінси:** у DDG-слайсі, не в SearXNG.
- **build_grid:** лише intent×audience; розмір; `BRANDS` ще імпортовний `brand_feed`.
- **config:** нові дефолти.
- **Зворотна сумісність DDG-only:** оновлений `test_wiring`.

## 7. Ризики

1. SearXNG upstream-бан (мітигації в 3.5).
2. Коротший `CRAWL_INTERVAL` → вищий throttle DDG/SearXNG — стежити за логами, за потреби відкотити (ops).
3. `budget` 80 серійно → прохід ×4 довший (серійна стеля — окремий трек #11).
4. Зміна advance-семантики зачіпає наявні тести (навмисно; оновлюємо).

## 8. Порядок реалізації

split (3) → бренди-з-осі (4) → ручки+TTL (5) → жива Docker-перевірка + OSM force-refresh. Merge `--no-ff` у main, push, канонічний ребілд crawler-образу.
