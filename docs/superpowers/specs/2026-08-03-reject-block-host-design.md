# Трек #12 — «Відхилити» (retrievable-кошик) + «Заблокувати» (хост у медіа-блокліст)

**Дата:** 2026-08-03
**Гілка:** `feat/reject-block-host` (від `main`)
**Тип:** backend + admin (Vue). **Краулер не змінюється.**

## Проблема

Кнопка «Відхилити» в адмінці зараз лише ставить `status=rejected` (`crud/offer.set_status`,
offer.py:278) — reject «згасає» як прапорець і нічого не навчає систему, а відхилені офери
ніде не видно в UI. Потрібні дві окремі, ортогональні дії модератора над сміттєвим офером:

1. **«Відхилити»** — м'яко прибрати офер із черги, скласти у **retrievable-кошик**, звідки його
   можна дістати назад; краулер уже не виносить той самий контент у чергу повторно.
2. **«Заблокувати»** — покласти хост джерела у **медіа-блокліст**, щоб краулер більше його не
   краулив.

## Рішення (рішення, ухвалені у брейнштормі)

- **Тригер блоку:** окрема свідома дія «Заблокувати» (не автоматично на кожен reject —
  reject буває з різних причин: нема знижки, дубль, протухло; авто-блок забанив би легітимні
  бізнес-хости).
- **Який хост:** `site_url`/provider-хост офера (фолбек: `site_url` першого `offer_link`).
- **Куди хост:** **одразу в активний блокліст** (`status=approved`), reuse наявного
  `blocked_host_crud.add_manual`. Оборотно через в'ю «Медіа-блокліст» (HostCandidatesView).
- **Наявні офери хоста при блоці:** **не чіпати** — «Заблокувати» додає лише хост. Офер
  прибирає окремий клік «Відхилити». Дві кнопки навмисно незалежні.
- **Рівень приглушення reject:** рівень сторінки/контенту. Той самий контент після reject не
  повертається в чергу (уже забезпечено `create_offer` гілка 1, offer.py:78-105); змінений
  контент пасивний краулер **пропонує знову** (уже забезпечено гілкою 5) — це бажана поведінка.
  **Змін у краулері не потрібно.**
- **Кошик відхилених:** reject уже soft (рядок живе), `GET /admin/offers?status=rejected` уже
  працює — треба лише вкладка + кнопка «Відновити».

## Обсяг

### НЕ робимо
- Жодних змін у краулері (суппресія за контентом і споживання блокліста вже існують: треки 22, 29).
- «Заблокувати» не змінює статус жодного офера.
- Не чіпаємо hard-delete (кнопка «Видалити» лишається окремою, для остаточного видалення).
- Не додаємо reason-таксономію reject (відхилено як зайве ускладнення).

### Частина A — «Відхилити» як retrievable-кошик (admin-only)
1. Третя вкладка **«Відхилені»** (`name="rejected"`) в `OffersListView.vue` поряд із
   «Опубліковані»/«На модерації».
2. Кнопка **«Відновити»** на рядках `rejected` → `POST /admin/offers/{id}/restore` →
   `set_status(pending_review)` → офер повертається в чергу на повторний розгляд.

### Частина B — «Заблокувати» (ядро #12)
1. Кнопка **«Заблокувати»** на рядках офера статусів `pending_review` та `published`,
   активна коли є придатний `site_url`.
2. Confirm-діалог (дія впливає на майбутній краулінг, хоч і оборотна).
3. `POST /admin/offers/{id}/block-host`:
   - вивести bare-host із `offer.site_url`; фолбек — `site_url` першого `offer_link`;
   - нема придатного хоста → `422` (`validation_error`);
   - `blocked_host_crud.add_manual(db, host, admin.id)` → статус `approved`;
   - офер **не чіпати**; повернути `BlockedHostOut`.

## API

| Метод | Шлях | Тіло | Відповідь | Дія |
|-------|------|------|-----------|-----|
| POST | `/admin/offers/{id}/block-host` | — | `BlockedHostOut` | host(site_url) → approved blocklist; офер незмінний |
| POST | `/admin/offers/{id}/restore` | — | `OfferOut` | `set_status(pending_review)` |

Обидва — під `Depends(get_current_admin)`, як решта admin-ендпоінтів.

## Наслідок робочого процесу
Типове прибирання сміттєвого офера = **два кліки**: «Заблокувати» (хост) + «Відхилити» (офер).
Кнопки незалежні — узгоджено з рішенням «Заблокувати = лише хост».
