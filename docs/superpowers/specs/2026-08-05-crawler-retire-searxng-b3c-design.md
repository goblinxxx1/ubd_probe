# Retire SearXNG → single-provider search → B3c due-query walking

**Дата:** 2026-08-05
**Гілка:** `feat/crawler-retire-searxng-b3c` (від `main`)
**Тип:** crawler-only. Backend/admin/public не змінюються.
**Попередні фази Треку B:** A, B1, B2, B3a, B3b — завершено й у `main`. Це — фінальна фаза
(B3c) плюс прибирання SearXNG, чия непридатність доведена наживо (див. «Діагностика»).

## Мотивація / діагностика (доведено наживо, 2026-08-05)

SearXNG, self-hosted, віддає **0 придатних результатів** для наших запитів. Root cause
встановлено систематичним налагодженням на живому контейнері `ubd_probe-searxng-1`:

- Дефолтні веб-рушії, які SearXNG проксує, захищаються від нашого вихідного IP:
  `google cse`/`brave` → `too many requests` (SearXNG сам suspend-ить рушій на 180с);
  `duckduckgo`/`startpage` → `CAPTCHA` (лог: `SearxEngineCaptchaException`).
- `bing` не блокує жорстко, але на **комерційні кириличні** запити віддає **decoy-мотлох**
  (напр. «знижка ветеранам» → нарди; «знижка ветерани» → китайські кінорецензії douban),
  тоді як нейтральні (`coffee`, `погода Київ` з `language=uk-UA`) отримують коректні
  результати. Тобто Bing тихо труїть результат скраперу — гірше за CAPTCHA.
- `wikipedia`/`wikidata` відповідають, але для комерційних оферів марні.

**Висновок:** SearXNG — це скрапер тих самих публічних рушіїв, що всі захищаються від
скрейпінгу; self-hosting не дає привілейованого доступу з нашого IP. Деградація
**структурна**, не тимчасова — сама не «відновиться» без платного API або резидентних
проксі (обидва відхилені користувачем). Тому SearXNG прибирається повністю.

**Важливий факт:** `search_providers` дефолт = `"duckduckgo"` — тобто SearXNG **наживо й так
не в активних провайдерах** (сервіс піднято лише профілем `crawler`). Прибирання коду
**не змінює живої поведінки пошуку**; це чистий рефактор + видалення інфри.

## Мета

1. Повністю прибрати SearXNG (код, тести, конфіг, інфру) і **переписати B2-машинерію
   блок-партиції/свапу**, яка існувала лише заради пари DDG↔searxng.
2. Реалізувати **B3c — due-query walking** на спрощеному одно-провайдерному обході: кожен
   прохід бере лише **прострочені/нешукані (due)** фрази, свіжі пропускає → щопрохід свіжа
   мережева робота, покриття само-вирівнюється під TTL.
3. **Гарантувати, що поведінка DDG не змінюється** — жодних крашів чи перебоїв активного
   пошуку (окрема жива верифікація).

## Фаза 1 — прибрати SearXNG + згорнути пошук до одного провайдера

### 1A. Видалити searxng-код
- `crawler/discovery/providers.py`: клас `SearxngProvider` і `elif name == "searxng"`-гілку
  в `build_search_plans`. Невідомий провайдер уже обробляється `else → log.warning` (граційно).
- `crawler/tests/test_searxng_provider.py` — **видалити файл**.
- `crawler/tests/test_build_plans.py`: прибрати `test_ddg_and_searxng_plans_distinct_cursors`,
  прибрати `searxng_url` з `_cfg`.
- `crawler/tests/test_build_provider.py`, `crawler/tests/test_provider_typeclass.py`: прибрати
  searxng-посилання (перевірити й почистити `searxng_url` у cfg-namespace).

### 1B. Згорнути B2-машинерію до одного курсора («переписати зміни під searxng»)
- `crawler/discovery/search_pass.py` → `SearchPass.run`: простий обхід одним провайдером —
  `next_batch(block_size, grid_cursor)` від **єдиного** курсора, advance-on-success.
  **Прибрати:** свап `((i+cycle)%n)`, інкремент `cycle`, багатоплановий `for`-цикл.
  `provider_for_site_query()` → повертає єдиний план (fallback без змін).
- `crawler/discovery/search_state.py`: **прибрати** `block_cursor`, `cycle`, `searxng_cursor`
  з `_EMPTY` і відповідні property/setter. Обхід іде по **`grid_cursor`** (семантично коректна
  назва «позиція в гріді»). Старий `search_state.json` зі зайвими ключами вантажиться без
  краху (`setdefault` додає лише відомі; зайві ігноруються). Живий ефект: обхід продовжиться
  з `grid_cursor` (наживо =80) замість `block_cursor` (=240) — нешкідливий відкат по
  кеш-свіжих фразах; Фаза 2 їх пропустить.
- `crawler/discovery/providers.py`: `SearchProviderPlan` — обрізати searxng-only поля
  (`cursor_key`, `reset` якщо стають зайві) до потрібного одному DDG-провайдеру
  (`include_pins`, `succeeded` лишаються). Мінімізувати churn: якщо поле ще читається в
  `search_pass`, лишити; інакше прибрати.

### 1C. Конфіг / інфра
- `crawler/config.py`: прибрати `searxng_url` (у `_RawSettings`, `Config`, `load_config`);
  прибрати мертвий `search_queries_per_pass` (не використовується після B2; per-pass рахунок
  дає `search_block_size=15` — throttle-безпечне число лишаємо як per-pass розмір обходу).
- `crawler/.env.example`: прибрати `SEARXNG_URL`, `SEARXNG_SECRET`.
- `docker-compose.yml`: прибрати сервіс `searxng`; у краулері прибрати `depends_on: searxng`
  та env `SEARXNG_URL`/`SEARXNG_SECRET`.
- Видалити теку `searxng/` (`settings.yml`).
- `RUN.md`, `README-docker.md`: прибрати searxng-розділи.

### DDG-safety (інваріант Фази 1)
Трасування доводить незмінність: із одним провайдером поточний `run()` уже вироджується
(`n=1` → член свапу `0` → `start=cursor`), тож DDG **вже** отримує `next_batch(bs, cursor)`+піни
і зсув `cursor+bs`. Згорнута версія дає **байт-ідентичний** список ключових слів і **той самий**
`discovery.run(keywords, known)`. `RotatingDdgProvider`+`SearchCache` (анти-throttle, backoff,
кеш, 5 бекендів) — **не чіпаються**. Регресійні тести фіксують цей інваріант.

### Чекпоінт Фази 1
`cd crawler && ./.venv/Scripts/python.exe -m pytest -q` — усі зелені. Деплой: канонічний
ребілд crawler-образу; `docker compose ... stop searxng && docker compose ... rm -f searxng`
(зупинити й видалити контейнер). **Жива верифікація:** підняти краулер, підтвердити, що
активний DDG-прохід виконується без винятків, `errors=0`, searxng-контейнера немає. Питаю
«продовжуємо B3c?».

## Фаза 2 — B3c: due-query walking (на одному DDG-провайдері)

### 2A. Freshness-леджер
Після прибирання searxng лишається **один** провайдер (DDG); його `SearchState.cache` — єдиний
леджер свіжості. Двозначності «чия свіжість» немає.

- `crawler/discovery/search_state.py`: додати `is_fresh(keyword, ttl_seconds) -> bool` — легка
  перевірка `ts` кеш-запису (реюз `_key`-нормалізації), без матеріалізації кандидатів.

### 2B. Walking-курсор зі скіпом свіжих
- `crawler/discovery/search_pass.py`: `SearchPass.run` сканує грід від `grid_cursor`, збирає
  до `block_size` **due** фраз (де `is_fresh(kw, ttl)` False), **свіжі пропускає**; курсор
  просувається на к-ть **проглянутих** (не лише зібраних). Стоп-умови: зібрано `block_size`
  due **АБО** проскановано `len(grid)` фраз (тихий прохід, якщо все свіже — коректно).
- Виродження: якщо всі фрази due — поводиться як поточний лінійний обхід (без шкоди/змін).
- Наслідок: TTL стає per-phrase кулдауном; кожен прохід = свіжа мережева робота; повний обхід
  простору перш ніж повторити.
- `block_size` (=`search_block_size`, 15) і `ttl` (`search_cache_ttl_hours`) — наявні ручки.

### Деталь узгодження курсора зі скіпом
Курсор має вказувати на **наступну непроглянуту** фразу. Скановані-й-пропущені свіжі фрази
лишаються «позаду» курсора й будуть переглянуті на наступній лапі (коли постаріють). Це
природно вирівнює період лапи під TTL при поточній пропускній здатності.

### Чекпоінт Фази 2
`pytest -q` зелений. Деплой: ребілд crawler; жива перевірка, що активний прохід бере лише
due-фрази (свіжі з кешу пропускаються, мережеві запити йдуть на прострочені).
