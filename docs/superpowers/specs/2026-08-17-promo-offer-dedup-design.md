# Цілісний дедуп промо-оферів (Витік 1) — Design

**Дата:** 2026-08-17
**Статус:** затверджено до планування

## Проблема

Черга модерації знову наповнюється дублями оферів з доменів, які **вже мають опублікований офер**. Аудит бази (38 pending, 30 published) показав: **15 із 26 pending-хостів уже присутні серед published**, з них 11 оферів — не-shadow дублі того самого промо, поданого зі СТОРІНОК, інших за опубліковану (апекс-домашня, `/pro-nas`, `/category/aktsii`, `/promotions`-індекс).

### Першопричина (доведено на живих парах)

Гілка **3c** дедупу в `create_offer` ([backend/app/crud/offer.py:239](../../../backend/app/crud/offer.py)) вимагає, щоб **лейбл знижки збігався байт-у-байт** (`_primary_disc_sig` включає нормалізований текст лейбла). Той самий промо, написаний **іншими словами** на різній сторінці → інший лейбл → дедуп не спрацьовує, хоча host і величина знижки однакові.

Доведені пари (`status id = discount`):
- `edclinic`: published `198`=15% і pending `289`=15% — та сама величина, різні слова лейбла → проскочив.
- `mate.academy`: published `172`=free і pending `291`=free — те саме, різні слова → проскочив.
- `shishkinn`: published `80`=15% і pending `284`=15% — різні слова → проскочив.

Два суміжні прояви тієї ж хвороби:
1. **shadow vs новий:** `285`(shadow 15%, supersedes `81`) і `286`(новий 15%, `/pro-nas`) — той самий промо; 3c ігнорує shadow як ціль дедупу (`supersedes_offer_id IS NULL`) → новий дублює те, що вже стоїть у черзі як зміна.
2. **мульти-знижка:** `tovpollar` published `181` несе і 30%, і 50%; pending `287`(50%)+`288`(30%) повторюють їх, але 3c звіряє лише ПЕРВИННУ знижку → пропускає.

## Продуктове правило (від власника продукту)

Бізнес-домен, у якого вже є published-офер, **може** давати ще один окремий офер — **але** треба співставляти **тексти І величину знижки**, щоб не дублювати одне й те саме, написане різними словами на різних сторінках.

Філософія при сумніві: **консервативно — сумнів → НЕ схлопувати** (краще лишити зайвий дубль у черзі, який модератор reject-не вручну, ніж мовчки прибрати справжній окремий офер, який уже не відновити).

## Рішення (огляд)

Замінити в гілці 3c точний-збіг-лейбла на: **той самий host + збіг величини (як множини) + текст-схожість ≥ поріг**. Текст-схожість — token-set **Jaccard** (підхід A: стійкий до порядку слів і перефразування, консервативний поріг реалізує «сумнів → не схлопувати»). Плюс розширити ціль дедупу на pending-shadow і порівнювати множину знижок замість первинної.

### Компоненти

#### 1. Новий модуль `backend/app/crud/dedup.py` (чисті функції, без БД)

Ізольований, легко юніт-тестований. `offer.py` імпортує з нього.

- `normalize_tokens(text: str | None) -> frozenset[str]`
  lowercase → прибрати пунктуацію → викинути малий курований **укр. стоп-лист** → токенізувати в множину. Стоп-лист: службові слова, що не несуть промо-змісту (`для`, `на`, `та`, `і`, `й`, `з`, `зі`, `у`, `в`, `що`, `як`, `до`, `від`, `по`, `за`, `є`, `а`, `або`, `при`, `не`). Тримати список коротким.

- `text_similarity(a: frozenset, b: frozenset) -> float`
  Jaccard: `|a ∩ b| / |a ∪ b|`. Обидві порожні → `0.0` (не збіг — консервативно).

- `discount_magnitudes(discounts, dt, dv) -> frozenset[tuple]`
  Множина `(discount_type, discount_value)` усіх знижок офера. Якщо `discounts` порожній — падаємо на одиничне `(dt, dv)`. Лікує мульти-знижку.

- `is_duplicate_promo(a_text, a_mags, b_text, b_mags, threshold) -> bool`
  `True`, якщо `a_mags ⊆ b_mags` **І** `text_similarity(a_text, b_text) >= threshold`.
  Субмножина: кандидат (`b`) уже покриває всі знижки нового (`a`); текст — вирішальний гард проти схлопування двох різних акцій однакового %.

**Поріг:** `settings.dedup_text_similarity_threshold`, дефолт **0.6** (консервативно). Тюниться в конфізі без деплою коду; фінальне значення підбирається на реальних 11 парах у TDD (усі доведені-однакові мають схлопнутись, дві різні акції по 10% — ні).

**Текст для порівняння:** нормалізований `description` (абзац знижки) + конкатенація `label` усіх знижок офера. **Не** `title` — він = бізнес-теглайн, однаковий на всіх сторінках домену, промо не розрізняє.

#### 2. Перероблена гілка 3c у `create_offer`

Місце: [backend/app/crud/offer.py:239-264](../../../backend/app/crud/offer.py).

- Гейт входу без змін: `if crawler and not blocked and data.discount_type is not None`.
- Обчислити `host`, `new_text = normalize_tokens(description + labels)`, `new_mags = discount_magnitudes(...)`.
- Кандидати: той самий host, `created_by == crawler`, `status != expired`. **Прибрати** фільтр `supersedes_offer_id IS NULL` → у ціль потрапляють і pending-shadow (лікує `285/286`).
- Для кожного кандидата (за зростанням `id`): якщо `is_duplicate_promo(new_text, new_mags, cand_text, cand_mags, threshold)` → bump `last_seen_at`, `commit`, повернути наявний рядок (як робить чинна 3c).
- Якщо жоден не збігся — керування падає далі (гілка 4 / фінальний INSERT), без змін.

Host-кандидати кандидата обчислюються так само, як для нового (`_source_host(site_url) or _source_host(article_url)`).

#### 3. Разова чистка наявної черги — `backend/app/scripts/dedup_queue.py`

CLI-скрипт для очищення вже накопичених ~11 дублів.

- Вибрати всі `pending_review` крауленого походження (`created_by == crawler`).
- Згрупувати по host; у групі попарно застосувати `is_duplicate_promo`; лишити **1 представник/групу** (найменший `id` — найстаріший), решту дублів → `status = rejected`.
- **Dry-run за замовчуванням**: друкує, що саме схлопне (`id → зберігається id`), нічого не змінює. `--apply` виконує реально.
- Ідемпотентний: повторний запуск на вже-очищеній черзі нічого не робить.

#### 4. Конфіг

Додати `dedup_text_similarity_threshold: float = 0.6` у `backend/app/config.py` (Settings). Прочитувати в `create_offer` і в скрипті чистки.

## Дані / потік

Краулер → `POST /api/internal/offers` → `create_offer` → гілки `1 → 2 → 3 → 3b → 3c(нова) → 4 → INSERT`. Зміна ізольована в 3c + новий модуль. Публічний і адмін-шляхи не зачіпаються. Схема БД не змінюється (міграція не потрібна).

## Тестування (TDD — спершу червоні)

**Юніт (`backend/tests/test_dedup.py`):**
- `normalize_tokens`: стоп-слова викидаються, пунктуація прибирається, регістр знижується.
- `text_similarity`: ідентичні множини = 1.0; неперетинні = 0.0; перефразовані (спільне ядро) > 0.6; дрібно-різні < 0.6.
- `discount_magnitudes`: мульти-знижка → множина всіх пар; порожній `discounts` → падіння на `(dt,dv)`.
- `is_duplicate_promo`: субмножина+високий текст = True; та сама величина, різний текст = False; надмножина знижок = False.

**Інтеграція (`backend/tests/test_offer_dedup.py`):**
- Реальні пари як фікстури: `edclinic 289/198`(15%), `mate 291/172`(free), `shishkinn 284/80`(15%) → **схлопуються**.
- **shadow-vs-новий**: новий 15% з `/pro-nas` при наявному pending-shadow 15% → повертає shadow (`286→285`).
- **мульти-знижка субмножина**: новий 30% при published `{30,50}` → схлопується (`288→181`).
- **негатив**: дві різні акції по 10% з одного host, різний текст-опис → лишаються ДВА окремі офери.
- **негатив**: та сама величина, але текст нижче порога → не схлопується.

**Скрипт чистки (`backend/tests/test_dedup_queue_script.py`):**
- Насіяти дубль-групу; dry-run нічого не змінює; `--apply` лишає 1/групу, решту → rejected; повторний `--apply` ідемпотентний.

Запуск (з `backend/`, потрібен `mysql-container` на :3306): `./.venv/Scripts/python.exe -m pytest -q`.

## Ризики

- 🟡 Поріг 0.6 може лишити частину сильно-перефразованих дублів у черзі (свідомий наслідок «сумнів → не схлопувати»); значення тюниться в конфізі на реальних даних.
- 🟢 Субмножина-величин + текст-гард не дають схлопнути дві різні акції однакового %.
- 🟢 Чистка dry-run-first — нічого не втрачається наосліп.
- 🟢 Зміна ізольована в 3c + новий модуль; інші гілки дедупу й немодераційні шляхи недоторкані.
